# Архитектура платформы FuelPay System

**Назначение:** мультитенантная SaaS-платформа приёма наличных платежей за топливо (метан, пропан, бензин, дизель) на АЗС Узбекистана, с фискализацией через ОФД под маркетплейс-регистрацией платформы и последующими расчётами с АЗС через банк.

**Целевые платформы клиента:** Android (POS-терминалы, сенсорный экран, приоритет №1) и Windows (ноутбуки админов/операторов).

## 3. Мультитенантность и модель фискализации

Ключевая архитектурная развязка, которую вы описали: **платформа зарегистрирована в налоговых органах как маркетплейс**, а каждая подключённая АЗС имеет **свой виртуальный кассовый модуль**, привязанный к этой маркетплейс-регистрации — так обороты корректно относятся к АЗС (её ИНН), а не к юрлицу платёжного сервиса.

Практическая реализация:

- Таблица `stations` хранит для каждой АЗС: `inn`, `legal_name`, `legal_address`, `bank_account`, `mfo` (банковский идентификатор), и **`ofd_virtual_kassa_id` / `fiscal_module_id`** — идентификатор её виртуальной кассы у ОФД.
- Модуль **Fiscal Gateway Service** — единственная точка входа в ОФД. Он не хранит бизнес-логику расчёта, только: принимает `{transaction_id, station_id, items[], total, commission}` → подставляет `fiscal_module_id` нужной АЗС → отправляет запрос ОФД → получает `{fiscal_receipt_id, qr_code_url}` → возвращает.
- Такое разделение позволяет **сменить ОФД-провайдера, не трогая остальной backend** — важно, поскольку API конкретных операторов фискальных данных Узбекистана могут меняться, и точный контракт API нужно будет сверить с выбранным ОФД-провайдером на этапе интеграции (это то, что стоит уточнить отдельно перед реализацией — я не привожу конкретные эндпоинты, чтобы не выдавать непроверенную информацию за факт).
- QR-код кэшбэка от налоговой, который должен быть на чеке, приходит в ответе ОФД вместе с `fiscal_receipt_id` — Fiscal Gateway сохраняет его как часть записи транзакции и передаёт на клиент для печати.

## 4. Доменная модель (ключевые сущности)

```
User(id, login, password_hash, role, station_id?, phone, status[active/blocked], created_by)
Station(id, legal_name, inn, address, bank_account, mfo, ofd_virtual_kassa_id, status)
Product(id, name, category[metan|propan|benzin|dizel], unit, is_special, is_global_locked)
StationProductPrice(station_id, product_id, price, is_locked_by_admin, updated_by, updated_at)
Shift(id, station_id, operator_id, started_at, ended_at, shift_number)
Transaction(
  id, uuid_idempotency_key, shift_id, station_id, operator_id, product_id,
  amount_input_mode[separate|included], product_amount, commission_amount,
  total_amount, volume, status[pending|fiscalized|failed],
  fiscal_receipt_id, qr_code_url, created_at
)
CashHandover(id, shift_id, station_id, operator_id, declared_amount,
  receipt_photo_url, confirmed_by, confirmed_at, shortage_or_surplus, status)
Settlement(id, station_id, period_start, period_end, gross_amount,
  platform_commission, payout_amount, bank_transfer_id, status, executed_at)
Notification(id, from_user_id, to_user_id, message, thread_id, read_at, created_at)
AuditLog(id, actor_id, action, target_type, target_id, payload, created_at)
```

`Transaction.uuid_idempotency_key` генерируется на устройстве **до** отправки — если сеть оборвётся и клиент повторит запрос, backend не создаст дубль.

## 5. Поток: оплата → печать → фискализация

```
Оператор вводит сумму → расчёт (клиент, офлайн-способный)
        │
        ▼
Локальная запись в SQLite (status = pending, uuid сгенерирован)
        │
        ▼
Печать чека на 58мм принтер СРАЗУ (не ждём ответ ОФД — иначе очередь на кассе)
   ⚠ важно: чек печатается с пометкой "ожидает фискализации", QR подставится
   после ответа ОФД, либо чек допечатывается вторым QR-стикером/повторной печатью —
   это ключевое решение, которое нужно принять с учётом требований налоговой:
   можно ли печатать чек до получения фискального ответа, или обязательна
   синхронная фискализация до печати. Уточняется с ОФД-провайдером.
        │
        ▼
Фоновая отправка в Fiscal Gateway Service (если есть сеть)
        │
   ┌────┴────┐
   ▼         ▼
 Успех    Нет сети / ошибка ОФД
   │         │
   │         └─▶ остаётся в очереди retry (exponential backoff),
   │             статус "не фискализирован" виден в Истории платежей
   │             красным, и как только связь появится — сервис
   │             дожимает очередь автоматически
   ▼
status = fiscalized, qr_code_url сохранён, шифт-итоги обновлены
```

Такой порядок (печать сразу, фискализация асинхронно) даёт скорость на кассе, но требует юридической проверки — насколько это допустимо по требованиям Узбекистана к моменту выдачи чека клиенту.

## 6. Поток: сданная выручка (инкассация)

1. Оператор в конце смены видит сумму `Shift.total` в разделе "Сданная выручка".
2. Оператор физически сдаёт наличные и присылает фото квитанции банка **в Telegram-бота платформы**, привязанного к его логину.
3. Telegram Bot Service сохраняет фото в S3 и создаёт `CashHandover(status = pending_confirmation)`, дублирует уведомление Модератору/Гл. Админу в приложении.
4. Модератор (или Гл. Админ) открывает фото, вручную сверяет и подтверждает — заполняет `shortage_or_surplus` (может быть 0).
5. После подтверждения статус у Оператора и Админа АЗС становится зелёным, с суммой недостачи/переплаты рядом.

Это намеренно полу-ручной процесс (как вы и описали) — автоматизировать сверку с банковской квитанцией по OCR можно на будущих этапах, но не в MVP.

## 7. Поток: расчёты с банком (settlement)

Отдельный контур от инкассации — это уже про **безналичное перечисление между вашей компанией и АЗС**:

1. Наличные, собранные по всем АЗС, физически поступают на расчётный счёт компании-владельца платформы (через инкассацию/банк, вне приложения).
2. **Settlement Service** периодически (например, ежедневно/еженедельно — конфигурируется Гл. Админом) формирует по каждой АЗС: сумму подтверждённых `CashHandover` за период минус комиссия платформы = `payout_amount`.
3. Формируется батч на выплату → вызывается **Bank API** (интеграция зависит от банка — обычно это либо прямой API банка для массовых платежей, либо файл-выгрузка в формате банка для загрузки в банк-клиент).
4. Статус выплаты (`pending/sent/confirmed/failed`) хранится в `Settlement`, виден Гл. Админу и Админу АЗС (для своей станции) в отчётах.

Это — модуль с наивысшими требованиями к аудиту: каждое движение денег должно журналироваться в `AuditLog` с неизменяемой историей (append-only, никаких `UPDATE`/`DELETE` на финансовых записях — только компенсирующие проводки).

## 8. Backend: модульная структура

Рекомендация для старта — **модульный монолит на NestJS**, а не микросервисы с первого дня: команда небольшая, а межмодульные транзакции (например, оплата → обновление смены → уведомление) проще держать в одной БД с ACID-транзакциями, чем городить распределённые транзакции с первого релиза.

```
/apps/api
  /modules
    auth/              — логин, JWT, refresh, роли, permission-флаги
    users/              — Операторы, Админы АЗС, Модераторы, Гл. Админ
    stations/           — АЗС, реквизиты, привязка ofd_virtual_kassa_id
    catalog/            — товары, цены по станциям, локи (глобальный/локальный)
    shifts/              — учёт смен, нумерация с 00:01
    transactions/        — приём оплаты, идемпотентность, расчёт
    fiscal-gateway/      — интеграция с ОФД (изолированный адаптер)
    cash-handover/       — сданная выручка, Telegram-интеграция
    settlement/          — расчёты с банком, выплаты АЗС
    reporting/           — агрегации, Excel-экспорт, 58мм-отчёты
    notifications/       — чат Модератор↔Оператор (WebSocket)
    audit/               — неизменяемый журнал всех значимых действий
  /gateway               — API Gateway слой (rate-limit, auth middleware)
```

Когда нагрузка/команда вырастут — `fiscal-gateway`, `settlement` и `notifications` первыми кандидаты на вынос в отдельные сервисы (они уже изолированы по границам модуля и имеют собственные внешние интеграции).

## 9. Клиентская архитектура (Flutter)

- **Общее ядро** (модели, расчёт комиссии как чистая функция, offline-репозитории) — используется всеми ролями и обеими платформами.
- **Ролевые модули экранов** — отдельный "флейвор" интерфейса на роль (`operator_ui`, `station_admin_ui`, `moderator_ui`, `super_admin_ui`), но с переиспользуемыми виджетами (карточка товара, табло суммы и т.д.).
- **Адаптивный layout-слой**: `LayoutBuilder`/`MediaQuery` переключает между "desktop-с-клавиатурой" (Tab/стрелки/Enter, как в уже сделанном макете) и "touch-android" (экранный numpad, увеличенные тач-зоны) — общая бизнес-логика, разные обёртки ввода.
- **Локальная БД (SQLite/drift)**: таблицы-зеркала `transactions`, `shifts`, `sync_queue`. Всё, что уходит на сервер, сначала пишется локально с `pending`-статусом.
- **Sync Service**: фоновый воркер, слушает сетевое состояние, дожимает очередь (транзакции → ОФД, фото инкассации → Telegram/S3), обновляет статусы.

## 10. Безопасность

| Область | Решение |
|---|---|
| Аутентификация | JWT access (короткий TTL) + refresh token; офлайн-грейс-период с локально захэшированным паролем на ограниченное время |
| Авторизация | Permission-флаги в токене, проверка на backend на каждый эндпоинт (не доверять клиенту) |
| Хранение секретов | Ключи ОФД/банка — в secret manager (Vault/Cloud KMS), никогда не в клиентском коде |
| Идемпотентность | UUID на каждую транзакцию, генерируется на устройстве |
| Целостность финансовых данных | Append-only журнал для `Transaction`/`Settlement`/`AuditLog`; исправления — только компенсирующими записями |
| Транспорт | TLS everywhere; сертификат pinning на мобильном клиенте — желательно, учитывая финансовый характер приложения |
| Разграничение по станциям | Row-level scoping: Админ АЗС/Оператор физически не может получить данные другой станции даже при попытке подделать `station_id` в запросе — backend всегда сверяет с `station_id` из токена |
| Блокировки | Мягкая блокировка (`status = blocked`), не удаление — сохраняется история для аудита |
| Печать offline-чеков | Чек, распечатанный до фискализации, должен быть отличим (пометка) от финального — минимизирует риск при сверке |

## 11. Отчётность и печать

- **58мм чек** — ESC/POS, шаблон редактируется Гл. Админом с чекбоксами "неизменяемое / АЗС-специфичное" поле (как вы описали).
- **58мм отчёт смены** — отдельный компактный шаблон: кол-во транзакций, объём по видам топлива, сумма платежей, сумма комиссии, итог.
- **Excel-экспорт** — генерируется на backend (`reporting` модуль), отдаётся как файл через presigned S3 URL.
- **НДС 12%** считается отдельно от комиссии, только на сумму товара — отдельное поле в отчётах, не смешивается с суммой комиссии платформы.

### Открытые вопросы, которые нужно закрыть до старта разработки backend

1. Какой именно ОФД-провайдер/API используется для виртуальной кассы под маркетплейс-регистрацией — точный контракт API, обязательна ли синхронная фискализация до печати чека.
